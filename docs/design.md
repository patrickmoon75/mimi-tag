# 미미태그 MVP 설계

> 버전 0.1 · 2026-09-27 · 비공개 (통합 특허 출원 전 외부 공개 금지)

## 1. 한 줄 정의

작은 QR 스티커 하나를 물건에 붙이면, 그 물건의 **구매증명**, **선물 편지**, **분실 시 안심 연락**이 한 곳에 기록되고, 일정 기간이 지나면 기록이 **봉인**되어 누구도 바꿀 수 없으며, 물건이 다른 사람에게 넘어가면 기록이 **함께 승계**된다.

## 2. 구성

| 구성 요소 | 선택 | 이유 |
|---|---|---|
| 웹앱 | Next.js (App Router, TypeScript), 모바일 웹 | 앱 설치 없이 기본 카메라로 스캔 → 바로 열림 |
| 배포 | Vercel, 서울 리전 `icn1` | 서버 관리 없음. 개발 중 Hobby, 출시 시 Pro |
| DB·인증·파일 | Supabase, 서울 리전 `ap-northeast-2` | Postgres + 로그인(카카오) + 사진 저장을 한 곳에서 |
| AI 편지 초안 | 서버에서만 호출하는 LLM API | 키 노출 방지, 사용 횟수 제한 |

## 3. 보안 원칙 (레떼즈에서 얻은 교훈)

1. **공개 화면은 서버가 골라준 필드만 받는다.** 브라우저가 DB에서 행을 통째로 받는 일은 없다. (레떼즈 `/getUserInfo`가 휴대폰·생년월일을 통째로 돌려준 문제 재발 방지)
2. **봉인은 DB가 강제한다.** 앱 코드에 버그가 있어도 봉인된 기록은 DB 트리거가 수정·삭제를 거부한다.
3. **운영자도 편지·사진·연락처를 보지 않는다.** 관리자 화면은 발급·통계·상태만 다룬다.
4. **최소 수집.** 가입은 카카오 로그인만. 생년월일·성별·지역은 받지 않는다.
5. **코드는 추측 불가.** 8자리 랜덤(약 1조 가지) + 요청 빈도 제한.

## 4. 태그 코드 체계

```
https://MIMITAG.KR/S7K3M9QX2P
                   │└──┬───┘│
                   │ 랜덤 8자 └ 검증 문자 1자
                   └ 발행유형 1자
```

- 문자 집합: Crockford Base32 대문자 `0-9 A-Z` 에서 `I L O U` 제외 (32자). 헷갈리는 글자가 없고, **QR 영숫자 모드**로 인코딩되어 QR 칸 수가 줄어든다.
- 발행유형: `S` 스티커, `P` 제품 부착, `M` 판촉·단체.
- 국가·대상·납품처·배너는 **코드에 넣지 않고 발급 묶음(batch)에 기록**한다. 코드가 짧아야 1cm 인쇄가 가능하기 때문이다.
- 검증 문자: 앞 9자로 계산. 손으로 입력하거나 인식이 흐릿할 때 오타를 걸러 DB 조회 전에 거부한다.
- 전체 URL 약 30자 → QR 버전 2(25×25칸), 오류정정 M 수준에 들어간다.
- 주소는 대소문자 구분 없이 받아서 대문자로 통일한다.
- 기존 레떼즈 코드(16자리, `lettez.net/?sno=`)는 `legacy_sno`로 이관해 계속 열리게 한다.

## 5. 데이터 구조

```
batches ─┬─< tags ──1:1── assets ─┬── proofs (구매증명)
         │                        ├─< media (사진: 영수증/제품/편지)
         │                        ├─< letters (선물 편지)
         │                        ├─< ownership_events (소유 이력, 추가만 가능)
         │                        ├─< transfers (소유권 넘기기 요청)
         │                        └─< finder_threads ─< finder_messages
profiles (auth.users 1:1)
```

| 테이블 | 핵심 필드 | 비고 |
|---|---|---|
| `batches` | 발행유형, 국가, 대상, 제품명, 납품처, 배너 이미지·링크, 수량 | 관리자 전용 |
| `tags` | `code`(PK), batch, 상태(`issued`/`active`/`void`), `legacy_sno` | 스캔의 시작점 |
| `assets` | tag, 소유자, 이름, 용도(증명/편지/분실연락), 상태(`normal`/`lost`), `seal_at` | 태그 1개 = 자산 1개 |
| `proofs` | 구매처, 구매일, 금액, 보증기간, 시리얼, 금액 숨김 | 봉인 대상 |
| `media` | 종류, 저장 경로 | 봉인 대상 |
| `letters` | 받는 사람, 보내는 사람, 본문, 편지지, 배경음, 글꼴, 링크, 열람 수 | 봉인 대상 |
| `ownership_events` | 이전 소유자, 새 소유자, 종류(등록/선물/판매), 시각 | **수정·삭제 불가** |
| `transfers` | 요청자, 일회용 토큰, 방식(선물/판매), 금액 숨김, 만료, 수락자 | |
| `finder_threads` | 자산, 습득자용 비밀 토큰, 위치(선택) | 습득자는 토큰 링크로만 답장 확인 |
| `finder_messages` | 발신 측(습득자/주인), 본문 | |

## 6. 봉인 규칙

- `seal_at = 등록 시각 + 30일` (설정값, 확정 전 가정).
- `now() >= seal_at` 이후 `proofs`, `media`, `letters`에 대한 **수정·삭제를 DB 트리거가 거부**한다.
- 봉인 뒤에도 바뀔 수 있는 것: 자산 상태(분실 신고), 소유자(이전 시), 편지 열람 수, 새 편지 추가(새 편지는 자기 봉인 기간을 가짐).
- 소유 이력(`ownership_events`)은 처음부터 추가만 가능하다.

## 7. 스캔 한 번의 분기

```
/[code] 요청
  ├ 코드 형식·검증 문자 오류 → "올바르지 않은 태그"
  ├ tags 없음 / void        → "사용할 수 없는 태그"
  ├ 미등록(issued)          → 첫 스캔: 로그인 → 용도 선택 → 등록
  ├ 스캐너 = 소유자          → 내 태그 상세
  ├ 진행 중 선물 이전 있음    → 받는 사람 화면(편지 + 증명 받기)
  ├ 분실 신고 상태           → 습득자 화면(주인을 찾고 있어요)
  └ 그 외                   → 공개 화면(편지 공개 설정이면 편지, 분실 연락 켜짐이면 연락 버튼)
```

## 8. 소유권 이전과 승계

1. 소유자가 "넘기기 요청"을 만들면 일회용 토큰이 생긴다(7일 만료).
2. 받는 사람이 태그를 스캔하거나 토큰 링크를 열고, 로그인 후 **수락**한다.
3. DB 함수 하나(`accept_transfer`)가 한 트랜잭션으로: 소유자 변경 → 이력 추가 → 요청 종료.
4. 봉인된 구매증명·편지는 그대로 따라간다. 금액 숨김이면 새 소유자에게 금액이 보이지 않는다.

## 9. MVP에서 뺀 것

영수증 OCR, 카카오 챗봇·안심번호, 에스크로, 중고거래 플랫폼 연동, 분실 공고·장물 감시, 블록체인, 보험·광고·데이터 판매, 네이티브 앱.
